# Extraction, Formatting & Upsert Rules (`gcp-project-copilot`)

This reference defines the detailed extraction methodology, document scopes, naming conventions, and living-document synchronization rules for `gcp-project-copilot`.

---

## 1. Multi-Tab Google Meet Extraction Protocol

Meeting inputs are provided as Google Docs URLs generated by Google Meet (Gemini Notes + Transcript), formatted as `https://docs.google.com/document/d/<DOC_ID>`.

### Step 1.1: Inspect All Document Tabs
Google Meet documents contain **three distinct tabs** that must be listed using the `gdocs` CLI (`/google/bin/releases/gemini-agents-gdocs/gdocs`):

```bash
/google/bin/releases/gemini-agents-gdocs/gdocs readonly list-tabs <DOC_ID>
```

| Tab Index | Standard Tab Title | Content & Purpose in Analysis |
| :--- | :--- | :--- |
| **Tab 0** | `Quick notes` | Contains the official **Meeting Title**, **Session Date**, **Participant Smart Chips** (`[@handle](http://who/handle)`), thematic executive summary bullets, and **Next steps** action items. |
| **Tab 1** | `Full notes` | Contains detailed thematic paragraphs with speaker names and parenthetical timestamps `(HH:MM:SS)` referencing the transcript. |
| **Tab 2** | `Transcript` | Contains the verbatim chronological transcript segmented by `### HH:MM:SS` headings (`HEADING_3`) and `**Speaker Name:**` dialogue lines. |

### Step 1.2: Read All Three Tabs
Read each tab explicitly by passing `--tab <TAB_ID>`:
```bash
/google/bin/releases/gemini-agents-gdocs/gdocs readonly read <DOC_ID> --tab <QUICK_NOTES_TAB_ID>
/google/bin/releases/gemini-agents-gdocs/gdocs readonly read <DOC_ID> --tab <FULL_NOTES_TAB_ID>
/google/bin/releases/gemini-agents-gdocs/gdocs readonly read <DOC_ID> --tab <TRANSCRIPT_TAB_ID>
```

### Step 1.3: Resolve Deep-Linked Transcript Timestamps
In the `Transcript` tab, each timestamp block (`### HH:MM:SS`) is a Google Docs heading with a unique `#heading=h.xxxx` anchor. Whenever a timestamp is cited in the Questions Log, resolve its exact deep-link URL pointing directly to the `Transcript` tab heading:
```bash
/google/bin/releases/gemini-agents-gdocs/gdocs readonly get-url <DOC_ID> --tab <TRANSCRIPT_TAB_ID> --heading "<HH:MM:SS>"
```
*Resulting URL format*: `https://docs.google.com/document/d/<DOC_ID>/edit?tab=<TRANSCRIPT_TAB_ID>#heading=<HEADING_ID>`
*(Fallback: If a specific timestamp from `Full notes` does not match an exact `HEADING_3` string in `Transcript`, match the closest preceding `### HH:MM:SS` heading in the `Transcript` tab where the exchange begins, or link to `?tab=<TRANSCRIPT_TAB_ID>`).*

### Step 1.4: Evaluate Canonical Domain Taxonomy Fit (Interactive Gatekeeper)
Before generating any output files, map all extracted questions and topics against the **Canonical Architectural Domain Taxonomy** (`D1..Dn`) in `<workspace>/specs/specs_project.md`:
1. **Default — Keyword Expansion on Existing Domains**: If a new sub-topic shares the same governance boundary or core GCP service family as an existing domain `D#`, keep it inside `D#` and append the new keywords to `D#`'s `Core Technical Scope & Keywords` column in `<workspace>/specs/specs_project.md`.
2. **Candidate New Domain (`D(n+1)`) — Pause & Ask User**: If a meeting introduces a genuinely distinct architectural pillar (e.g., a dedicated agenda segment or $\ge 2$ technical questions that cannot reasonably fit `D1..Dn`), **pause before writing files** and use `ask_question` to let the user choose between:
   - **Option A**: Create new domain **`D(n+1): <Proposed Canonical Name>`** (logical slug: `` `<proposed-slug>` ``) in `<workspace>/specs/specs_project.md`.
   - **Option B**: Fold the topic/questions into existing domain **`D<X>: <Existing Domain Name>`** (expanding `D<X>`'s scope keywords).

## 2. Output Scope & Template Rules (Session-Level vs. Project-Level)

Outputs are divided into **two scopes** so that session-specific discussions are captured per meeting while project-wide directories (`members` and `glossary`) and cumulative logs (`questions-log` and `challenges`) are maintained in `<workspace>/project/common/`:

| Output Type | Canonical Template | Maintained Per-Meeting (`project/meetings/`)? | Maintained at Project Level (`project/common/`)? |
| :--- | :--- | :---: | :---: |
| **0. Meetings Registry (`meetings_registry`)** | [`template_meetings_registry.md`](../resources/templates/template_meetings_registry.md) | **No** *(Project-level only)* | **Yes** (`project/common/meetings_registry.md`) |
| **1. Stakeholder Roster (`members`)** | [`template_members.md`](../resources/templates/template_members.md) | **No** *(Project-level only)* | **Yes** (`project/common/project_members.md`) |
| **2. Customer Glossary (`glossary`)** | [`template_glossary.md`](../resources/templates/template_glossary.md) | **No** *(Project-level only)* | **Yes** (`project/common/project_glossary.md`) |
| **3. Technical Questions Log (`questions-log`)** | [`template_questions-log.md`](../resources/templates/template_questions-log.md) | **Yes** (`YYYYMMDD_questions-log_<slug>.md`) | **Yes** (`project/common/project_questions-log.md`) |
| **4. Topics & Challenges (`challenges`)** | [`template_challenges.md`](../resources/templates/template_challenges.md) | **Yes** (`YYYYMMDD_challenges_<slug>.md`) | **Yes** (`project/common/project_challenges.md`) |

### 2.1 Project-Level Only Outputs (`project/common/`)

#### A. Stakeholder & Participant Roster (`project/common/project_members.md`)
- **Template**: [`resources/templates/template_members.md`](../resources/templates/template_members.md)
- **Extraction & Upsert Rules**:
  1. **Cross-Reference Sources**: Combine the `@handle` chips at the top of `Quick notes`, speaker names in `Full notes` and `Transcript`, and the known stakeholder baseline in `<workspace>/specs/specs_project.md`.
  2. **One Row Per Person**: Never group multiple individuals into a single row.
  3. **Three Organizational Tables**:
     - **Section 1: Customer Stakeholders (`{{CUSTOMER_NAME}}`)**
     - **Section 2: Google Cloud Team**
     - **Section 3: External Partners & Newly Identified Participants** (for `.ext` contractors, system integrators, or newly discovered participants whose formal role is `[TBD - Inferred from context]`).
  4. **Alias Normalization (Stored Exclusively in `specs/specs_project.md`)**: Because `project/common/project_members.md` is an official, customer-facing project document, **never** include speech-to-text phonetic aliases or ASR misspellings in `project_members.md`. Maintain all phonetic aliases and ASR variants **exclusively** in the **Transcript Phonetic Alias & Handle Dictionary** inside `<workspace>/specs/specs_project.md` (Section 5), and use that dictionary to normalize speakers to their canonical names and official `@handle` / email in `project/common/project_members.md`.
  5. **Attendance & Role Updates**: For existing rows, append `YYYY-MM-DD` to `Sessions Attended / Referenced` and enrich `Domain & Project Responsibilities` if new ownership details emerged.

#### B. Customer Glossary of Terms (`project/common/project_glossary.md`)
- **Template**: [`resources/templates/template_glossary.md`](../resources/templates/template_glossary.md)
- **Extraction & Upsert Rules**:
  1. Scan `Quick notes`, `Full notes`, and `Transcript` for business acronyms, organizational initiatives, source systems, data product definitions, compliance standards, and customer-specific platform terminology.
  2. Classify each term into one of the **6 Canonical Glossary Topic Categories**:
     - **Category 1**: Programs, Initiatives & Organizational Entities
     - **Category 2**: Business Domains, Roles & Operational Concepts
     - **Category 3**: Source Systems & Data Ingestion Feeds
     - **Category 4**: Data Mesh, Data Products & Medallion Taxonomy (or Analytics / Agentic Business Cases)
     - **Category 5**: Security, Compliance & Governance Standards
     - **Category 6**: Platform, Cloud & AI Tooling Terminology
  3. **Upsert Logic**:
     - If a term already exists in `project/common/project_glossary.md`, refine its definition or architectural impact if new details emerged, and append the session date `YYYY-MM-DD` to `Sessions Referenced`.
     - If a term is new, insert a new row in the appropriate category table and increment the top `Glossary Overview by Topic Category` summary count.

### 2.2 Per-Meeting Outputs (`project/meetings/YYYY-MM-DD_<slug>/`) + Project-Level Sync

#### A. Technical Questions Log (`questions-log`)
- **Template**: [`resources/templates/template_questions-log.md`](../resources/templates/template_questions-log.md)
- **Extraction & Formatting Rules**:
  1. **Metadata Table**: Include `Source Document` (link to the Google Doc), `Session Date`, `Scope`, and `Note`.
  2. **Session Overview & Question Summary Table**: Summarize all questions grouped by the **Canonical Architectural Domains** (`D1..Dn`) and **Project Governance Domain** (`P1`) defined in `<workspace>/specs/specs_project.md`, listing `Code Range` (e.g., `D1-Q01..D1-Q05`, `P1-Q01..P1-Q02`), `Core Technical Focus Areas`, and `Total Raised` per category.
  3. **Comprehensive Question Extraction & `D1..Dn` vs. `P1` Classification**:
     - Scan both `Full notes` and the verbatim `Transcript` to capture **all** technical, architectural, governance, security, FinOps, and project organization questions raised by customer, Google Cloud, or partner participants.
     - **Route Technical Architecture Questions to `D1..Dn`**: Questions about cloud services, data modeling, security, governance, quality, observability, AI agents, or BI belong in `D1..Dn`.
     - **Route Project Organization & Coordination Questions to `P1` (`Project Organization, Workstream Alignment & Delivery Governance`)**: Questions about engagement roadmap/milestone prioritization, workshop cadence or review slot scheduling, cross-workstream alignment (e.g., bridging two project workstreams around a shared vertical), or deliverable/schema handoff logistics (often raised by Google Cloud or program leads) belong in **`P1`**.
     - Formulate each question as a clear, self-contained, bolded question (preserving specific context such as data volumes, customer source systems, compliance standards, and GCP services).
     - Omit conversational filler or direct answers from the question text itself so the log remains a clean question inventory.
  4. **Permanent Domain-Scoped Reference Code (`[D#-Q##]` / `[P1-Q##]`), Attribution & Deep-Linked Timestamp**:
     - Assign every question a permanent, append-only **Domain-Scoped Reference Code** formatted as `` `[<DOMAIN_ID>-Q<NN>]` `` (zero-padded 2-digit counter per domain, e.g., `[D1-Q01]`, `[D1-Q02]`, ..., `[P1-Q01]`), numbered sequentially in chronological order across the project.
     - Use the **exact same code** for a given question in both its per-meeting file (`YYYYMMDD_questions-log_<slug>.md`) and the master `project/common/project_questions-log.md` so any question can be unambiguously referenced anywhere in the repository.
     - `**Asked By:** First LASTNAME` (uppercase last name matching template convention).
     - `**Timestamp:** [Timestamp HH:MM:SS](https://docs.google.com/document/d/<DOC_ID>/edit?tab=<TRANSCRIPT_TAB_ID>#heading=<HEADING_ID>)`

#### B. Prioritized Topics, Challenges & Exploration Roadmap (`challenges`)
- **Template**: [`resources/templates/template_challenges.md`](../resources/templates/template_challenges.md)
- **Extraction & Formatting Rules (Separating Customer-Led vs. Google-Led Segments)**:
  1. **Header Block & Session Presentation Flow Table**:
     - Include `# {{PROJECT_NAME}}: Prioritized GCP Topics & Exploration Roadmap`, `**Context:**`, `**Reference Document:**`, and `**Participants & Key Stakeholders:**`.
     - Immediately below the header in **per-meeting files** (`YYYYMMDD_challenges_<slug>.md`), include the **`## Session Structure & Presentation Flow (Customer-Led vs. Google-Led)`** table breaking the meeting into its chronological segments (`Customer-Led ({{CUSTOMER_NAME}})` vs. `Google-Led (Google Cloud)`), listing `Time Range`, `Lead Presenter(s)`, `Segment Focus, Demos & Artifacts Shown`, and `Primary Domains`.
  2. **Thematic Synthesis & Prioritization**: Group the meeting's technical discussions into prioritized major topics mapped to canonical domains (`## 1. <Topic Title> (D#)`, `## 2. <Topic Title> (D#)`, ...), separated by `---`.
  3. **Four Mandatory Role-Attributed Subsections per Topic**:
     To prevent mixing what the customer presented/built with what Google Cloud recommended, every topic MUST be divided into four distinct subsections:
     - `### 1. Customer Current State, Implementations & Ambitions ({{CUSTOMER_NAME}}-Led)`: Bullet points documenting the customer's existing architecture, live demos, slide proposals, data models, current tools, and business/technical ambitions presented during the session.
     - `### 2. Core Architectural Challenges & Friction Points`: Bullet points isolating the specific technical bottlenecks, scalability limits, governance gaps, compliance constraints, or architectural trade-offs that need to be solved.
     - `### 3. Google Cloud Architectural Solutions & Recommendations (Google-Led)`: Bullet points detailing the Google Cloud reference architectures, service patterns, best practices, and trade-off recommendations presented by Google Cloud architects during the session.
     - `### 4. Proposed Exploration Roadmap & Action Items (Owner-Attributed)`: Concrete, actionable next steps, PoCs, validation tests, architecture diagrams, or workshops agreed during the session, explicitly prefixed with the lead owner tag: **`[Google Cloud — <Name>]`**, **`[{{CUSTOMER_NAME}} — <Name>]`**, or **`[Joint — <Names>]`**.

## 3. Directory Naming & Relative Path Rules

1. **Meeting Folder Name**: `project/meetings/YYYY-MM-DD_<meeting-slug>/`
   - `YYYY-MM-DD`: ISO 8601 session date extracted from the meeting notes.
   - `<meeting-slug>`: 3–5 word lowercase `kebab-case` identifier summarizing the session focus. Strip generic prefixes like `{{CUSTOMER_NAME}}-google` or `meeting-notes`.
2. **Per-Session Output Filenames**:
   - `<YYYYMMDD>_questions-log_<meeting-slug>.md`
   - `<YYYYMMDD>_challenges_<meeting-slug>.md`
3. **Relative Path Rule for All Workspace Markdown Links**:
   - Every internal file or directory reference across `<workspace>/specs/specs_project.md`, `project/common/`, `project/meetings/`, and `project/topics/` MUST use **portable relative paths** (e.g., `../project/common/project_members.md`, `../meetings/YYYY-MM-DD_<slug>/...`).
   - **Never** write `file:///` URIs or absolute filesystem paths (`/usr/...`) inside repository Markdown files.

## 4. Parallel Common Project Documents Synchronization Rules (`project/common/`)

### Rule 4.1: Update `project/common/meetings_registry.md` (Idempotency Gate)
- Check if `<DOC_ID>` already exists in `meetings_registry.md`.
- If it is a new meeting, add a new row to the registry table with `#`, `Date`, `Meeting Title` (linked to the Google Doc), `Google Doc ID`, `Slug`, relative links to `[Questions Log (<count>)](...)` and `[Challenges (D#...)](...)` in `../meetings/YYYY-MM-DD_<slug>/`, and `Status = Complete`.
- If `<DOC_ID>` was already analyzed, update its existing entries in `project/common/` in-place rather than duplicating rows or questions.

### Rule 4.2: Upsert `project/common/project_members.md` & Sync Aliases to `specs/specs_project.md`
- Update `Sessions Attended / Referenced`, enrich roles/scopes for existing participants, and insert any newly discovered participants in `project/common/project_members.md` using only canonical names and official handles/emails.
- Append any newly discovered transcript phonetic aliases or ASR variants **exclusively** to Section 5 of `<workspace>/specs/specs_project.md` (never in `project_members.md`).

### Rule 4.3: Upsert `project/common/project_glossary.md`
- Insert newly discovered terms across the 6 topic categories or enrich existing definitions and append `YYYY-MM-DD` to `Sessions Referenced`.

### Rule 4.4: Aggregate `project/common/project_questions-log.md` (With Permanent `[D#-Q##]` / `[P1-Q##]` Codes)
- Maintain the cumulative inventory of all technical and project organization questions across the project, grouped by the **Canonical Architectural Domains** (`D1..Dn`) and **Project Governance Domain** (`P1`) defined in `<workspace>/specs/specs_project.md`.
- Under the matching Domain section, append each new question using the next sequential domain-scoped code (`[<DOMAIN_ID>-Q<NN>]`) and the multi-session format:
  ```markdown
  * **`[<DOMAIN_ID>-Q<NN>]` <Question Text>**
    * **Asked By:** First LASTNAME
    * **Session:** [YYYY-MM-DD (<meeting-slug>)](../meetings/YYYY-MM-DD_<slug>/YYYYMMDD_questions-log_<slug>.md)
    * **Timestamp:** [Timestamp HH:MM:SS](https://docs.google.com/document/d/<DOC_ID>/edit?tab=<TRANSCRIPT_TAB_ID>#heading=<HEADING_ID>)
  ```
- Update the `Code Range` and `Total Raised` counts in the top `Project Question Summary` table.

### Rule 4.5: Evolve `project/common/project_challenges.md`
- `project_challenges.md` is a **living architectural synthesis**, not a raw concatenation of meeting files.
- When a meeting addresses an **existing topic section** (`D1..Dn`), preserve the **4-subsection role-attributed structure**:
  1. **Sessions Covered**: Append the new meeting date and link to the topic's `**Sessions Covered:**` metadata line.
  2. **Deep-Dive Deliverables**: If a corresponding folder exists under `project/topics/<topic-slug>/`, link it under `**Deep-Dive Deliverables:**`.
  3. **1. Customer Current State, Implementations & Ambitions (`{{CUSTOMER_NAME}}`-Led)**: Merge newly presented customer architectures, implementations, or evolving business objectives (tagged with `[YYYY-MM-DD]`).
  4. **2. Core Architectural Challenges & Friction Points**: Merge newly uncovered nuances, edge cases, or constraints (tagged with `[YYYY-MM-DD]`) without deleting still-valid challenges from earlier sessions.
  5. **3. Google Cloud Architectural Solutions & Recommendations (`Google-Led`)**: Expand with newly presented GCP reference architectures, patterns, or architectural decisions (tagged with `[YYYY-MM-DD]`).
  6. **4. Proposed Exploration Roadmap & Action Items (`Owner-Attributed`)**: Update the owner-tagged roadmap bullets (`[Google Cloud — <Name>]`, `[{{CUSTOMER_NAME}} — <Name>]`, `[Joint — <Names>]`)—adding newly agreed action items and marking previously proposed items if completed or superseded.

### Rule 4.6: Atomic 4-File Propagation for Newly Approved Domains (`D(n+1)`)
When the user approves a new domain `D(n+1)` during **Step 1.4**:
1. **`specs/specs_project.md` (Section 3)**: Append `D(n+1)` to the **Canonical Architectural Domain Taxonomy** table with its `Canonical Domain Name`, plain-text logical `project/topics/` Directory Slug (`` `<new-slug>` ``), and `Core Technical Scope & Keywords`.
2. **Per-Meeting Outputs (`project/meetings/YYYY-MM-DD_<slug>/`)**: Include `D(n+1)` in the session's `YYYYMMDD_questions-log_<slug>.md` and `YYYYMMDD_challenges_<slug>.md`.
3. **`project/common/project_questions-log.md`**: Add a `D(n+1)` row to the top `Project Question Summary` table (setting prior session counts to `0`) and append `# D(n+1). <Canonical Domain Name>` at the end of the file.
4. **`project/common/project_challenges.md`**: Add a `D(n+1)` row to the `Architectural Challenge Overview` table and append `# D(n+1). <Canonical Domain Name>` (using the 4-subsection template) at the end of the file.
5. **Lazy `project/topics/<new-slug>/` Folder Creation**: Do **not** create an empty directory under `project/topics/` when registering `D(n+1)`. Only create `project/topics/<new-slug>/docs/` when a deep-dive deliverable is actually generated.
